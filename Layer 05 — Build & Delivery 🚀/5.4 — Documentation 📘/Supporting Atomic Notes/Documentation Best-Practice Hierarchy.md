Documentation Best-Practice Hierarchy

1. **README.md** → What this project is and how to run it. – (effective README structure examples GitHub)
2. **ARCHITECTURE.md** → How the system is structured and _why_ it’s designed that way. – (software architecture documentation guide)
3. **CONTRIBUTING.md** → How to build, test, and deploy safely. – (open source contributing guide format)
4. **CHANGELOG.md** → What changed and when, using semantic versioning. – (keep a changelog format)
5. **In-Code Comments** → Explain _why_ something exists when not self-evident. – (when to comment code best practices)

> **Rule:** Documentation should lower cognitive load, not add it.
> When it takes longer to understand _the docs_ than _the code_, the docs have failed.
